# P0C: multiMAN-mode experiment (2026-10-31)

Setup: PS2 DVD (SLES_509.92, single layer) inserted throughout. mmCM 04.75 (BLES80608) installed; its menu has "Switch to multiman mode - restart mmCM into standard CFW mode". Probe v2 (append log) run before and after; log copy `local_only/probe_v2_cumulative.log`; photos `local_only/photos/20261031_1303*.jpg`.

## Results

- **PROVEN (photos):** after switching, multiMAN's hex viewer ("file view") shows `/dev_bdvd` `SYSTEM.CNF` contents: `BOOT2 = cdrom0:\SLES_509.92;1`, `VER = 2.00`, `VMODE = PAL` (55 bytes). So multiMAN can read PS2 file data from this drive. Which viewer mode / read path it used is UNKNOWN (only "file view" was intended).
- **PROVEN (log):** probe run BEFORE (no multiMAN): reads lba 0/16/17/last = `8001002F`, file read `8001002B`, GET CONFIGURATION all zeros (profile 0000).
- **PROVEN (log):** probe run AFTER (multiMAN exited to XMB, nothing launched/ejected): reads lba 0/16/17/last STILL `8001002F`, file read STILL `8001002B`, but GET CONFIGURATION now returns real data, current profile 0x0010 (DVD-ROM) with feature list (`FF71`, `FF70`, `FF61`, `FF60`, `FF50`). Only these lines differ between the two runs.

## Interpretation (INFERRED)

- Drive/LV2 state changed after the mode switch (GET CONFIGURATION is no longer zero-filled), consistent with Cobra's PS2 zero-fill being disabled or a drive reset happening in "standard CFW mode".
- That change alone did NOT make `sys_storage_read` (our probe's path) or a plain file read work. multiMAN reads the data through something our probe does not do (own patches active only while running, different flags/region, a Cobra/LV2 syscall, or a different file route). UNKNOWN which.
- Still says nothing about the netemu LV1 partition.

1. **INFERRED — ordinary LV2 ABI:** [IRISMAN `master`, include/storage.h](https://raw.githubusercontent.com/aldostools/IRISMAN/master/include/storage.h), `sys_storage_open` (154–158), `sys_storage_read` (168–172), `sys_storage_close` (161–165). Quoted line: `lv2syscall4(600, id, 0, (uint64_t) fd, 0);`. The optical ID is `0x0101000000000006`; output is an `int` storage handle, not an Fs file descriptor or LV1 device ID. Read is **602 `(fd,0,start_sector,sectors,user_buffer,&u32_sectors_read,0)`**; open is **600 `(id,0,&int_handle,0)`**; close is **601 `(handle)`**. No explicit region selector, alignment minimum or universal transfer limit is established by this header. The second read argument is zero, not demonstrated to be an LV1 region. These match v2; v3 varies count, alignment and handle lifetime only. The header's forbidden setup adapters are 864 `(0x5004,0x29)` reset, `(0x5004,0x46)` authentication, and `(0x5007,&three_u64s)` control; only the first control word is initialized there. None was copied.

2. **INFERRED — PS1/CD reader and setup:** [IRISMAN `master`, source/psx.c](https://raw.githubusercontent.com/aldostools/IRISMAN/master/source/psx.c), `get_psx_region_cd` (2449–2492), uses a **16-byte-aligned 4096-byte buffer**, BD handle, one-sector 602 reads at 4/16 with the flag-zero wrapper. `read_raw_sector_bdvd` (2530–2557) instead uses **604 `(handle,1,&packet,56,buffer,sector_size*count)`**: READ CD `0xBE`, 12-byte CDB, LBA at bytes 2–5, count at 6–8, byte 9 `0xF8`, byte 10 `2`, protocol **3/DMA**, direction **1/inbound**, block count/size supplied separately. `copy_PSX_game_from_CD` allocates `memalign(16,1024*0x940)` and caps batches at 1024; this is a caller limit, not a universal syscall limit. `Reset1_BDVD` does reset/authenticate/control `0x3F`; `Reset2_BDVD` does reset/control `0x43`/control `0x3F`. Quote near the reader: `// from Multiman modified by Estwald`. **UNKNOWN:** equivalence to modern multiMAN or a PS2 DVD dumper. No raw-CD stage was added.
